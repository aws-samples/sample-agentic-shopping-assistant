# Evaluations

[한국어](evaluations.ko.md)

ARIA uses AgentCore Evaluations in two ways. Both use the same evaluators, so their scores are comparable.

| | Online evaluation | Dataset evaluation |
| --- | --- | --- |
| What it scores | A sample of live sessions, continuously | A fixed set of test conversations, on demand |
| Where it lives | `packages/infra` (`EvaluationsStack`), configured under `[evaluations]` | `packages/agent/evals`; see [dataset evaluations](#dataset-evaluations) |
| Ground truth | None: the judges infer the shopper's goal | Your `assertions`, `expected_trajectory` and `expected_response` |
| Good for | Spotting drift and regressions in real traffic | Release checks, prompt and model changes |

This guide covers both modes, which share the prerequisites below.

## Prerequisites

- **Approved content capture.** `operations.captureContent = true` stores prompts, responses and tool results in the Runtime log group (30-day retention). Get storage and retention approved first (see [operations](operations.md)). Without captured content, there's nothing to score.
- **Transaction Search delivering to CloudWatch Logs** in the deployment region. This app doesn't change that account-level setting. Check it with `aws xray get-trace-segment-destination --region <region>`; it must show `"Destination": "CloudWatchLogs"` and `"Status": "ACTIVE"`. The destination can differ between regions in the same account. Set `operations.transactionSearchReady = true` only after checking; `scripts/preflight.py` checks again when evaluations are enabled.
- **Judge model access.** The default judge is `global.anthropic.claude-haiku-4-5-20251001-v1:0`. `aws bedrock get-foundation-model-availability --region <region> --model-id anthropic.claude-haiku-4-5-20251001-v1:0` should report `AUTHORIZED` and `AVAILABLE`.
- **A judge budget.** Each scored session costs judge calls. Trace-level evaluators run once per turn, tool-level evaluators once per tool call, and session-level evaluators once per session. With the six default evaluators, one two-turn session with three tool calls produced 13 scores.

## Turning it on (two deploys)

`operations.traceLogGroup` must name the Runtime's own log group, `/aws/bedrock-agentcore/runtimes/<RuntimeId>-DEFAULT`, and the Runtime ID is generated by the first deploy. So it takes two deploys:

1. Deploy with `captureContent = true`, `transactionSearchReady = true` and `[evaluations] enabled = false`, following the plan and deploy steps in [release](release.md#manual-deployment).
2. Read the `RuntimeId` output of the `<ns>AgentRuntime` stack. Send one test conversation. Then run this CloudWatch Logs Insights query against the Runtime log group to confirm the spans are there, under the service name the stack will filter on (`<runtime name>.DEFAULT`, which is `ariadev_agent.DEFAULT` for the Dev template):

   ```
   fields @message
   | filter ispresent(spanId)
   | stats count(*) by resource.attributes.service.name
   ```

   On a unified Runtime, `aws/spans` can exist and stay empty. That's expected.
3. Set `operations.traceLogGroup` to that log group and `[evaluations] enabled = true`, and choose `samplingPercentage` and the evaluators (at most 10, custom ones included). Then plan and deploy again. This adds the `<ns>Evaluations` stack.

If the Runtime is ever replaced and gets a new `RuntimeId`, update `traceLogGroup` and redeploy. Otherwise the old name keeps matching nothing, and nothing reports an error.

## Checking that sessions are scored

- A session is scored after it has been idle for `sessionTimeoutMinutes`, and processing adds more delay. In the verification run, results appeared about 15 minutes after the last turn, with a 5-minute timeout.
- Results are JSON events in the stack's results log group, `/<ns>/evaluations/results` (the `ResultsLogGroupName` stack output). Summarize them with Logs Insights:

  ```
  fields attributes.session.id, attributes.gen_ai.evaluation.name,
         attributes.gen_ai.evaluation.score.value, attributes.gen_ai.evaluation.score.label
  | sort @timestamp desc
  ```

  The judge's reasoning is in `attributes.gen_ai.evaluation.explanation`.
- Scores are also published as CloudWatch metrics in the `Bedrock-AgentCore/Evaluations` namespace, and appear in the CloudWatch console under GenAI Observability → Bedrock AgentCore → your agent → Evaluations.
- Measure coverage by comparing scored sessions with the sessions in the Runtime log group. Zero scored sessions is a failure to investigate, not a clean result.
- To verify a new setup on a non-production stage, raise `samplingPercentage` to 100 and lower `sessionTimeoutMinutes` while only test traffic flows. Restore both afterward.

**Retention.** Judge explanations restate parts of the conversation, so the stack writes results to its own log group with 30-day retention, matching the Runtime log group. Left to itself, the service would create a results log group that never expires. The group is retained when the stack is deleted.

## Reading the scores

Online evaluators have no ground truth, so they judge whether the shopper's goal was met, not whether the agent did what you intended. A search that honestly finds nothing can score 0 on `Builtin.GoalSuccessRate`: the agent searched with the right filters and said nothing matched, but the judge marks the goal as not met because the agent didn't broaden the search or suggest alternatives. A dataset run of the same conversation scores 1.0 against an assertion that only requires an honest "nothing found". Read low scores together with their explanations: some point at catalog coverage or product decisions rather than agent bugs.

## Custom evaluators

Add a `CustomEvaluatorSpec` to `packages/infra/components/evaluators.py`. It's deployed with the Evaluations stack and attached to the online configuration. The shipped example, `catalogue_grounding`, checks that every product the assistant names came back from search.

- Placeholders take single braces: `{context}` and `{assistant_turn}` (TRACE); `{context}` and `{available_tools}` (SESSION); `{context}`, `{available_tools}` and `{tool_turn}` (TOOL_CALL). Double braces fail at deploy with "Instructions contain invalid placeholders".
- Don't add output-format instructions; the service appends its own instruction asking for a reason and a score.
- Ground-truth placeholders (`{assertions}`, `{expected_response}`, `{expected_tool_trajectory}`) can't be used in online configurations.
- To use a custom evaluator in dataset runs, pass its ID from the `CustomEvaluatorIds` stack output to `python -m evals.run --evaluator`.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| No results log group, or no events | Wait past `sessionTimeoutMinutes` plus processing time. Then check sampling, the `EvaluatedServiceName` stack output against the spans' `resource.attributes.service.name`, that `traceLogGroup` still names the current Runtime, `captureContent`, and the Transaction Search destination. |
| `CREATE_FAILED` on a custom evaluator: "invalid placeholders" | Use single braces, and only placeholders that the evaluator's level allows. |
| Error events in the results log group | Judge model access, quotas and throttling in the region. |
| Every session scores perfectly | Check coverage and read a few explanations before trusting it. The sample may be small or unrepresentative. |

## Turning it off

Set `[evaluations] enabled = false` and deploy. The app then leaves out the Evaluations stack, but a deploy never deletes a stack the app no longer contains, so the online configuration and custom evaluators keep running until you delete the `<ns>Evaluations` stack yourself (Prod stacks have termination protection, which must be turned off first). To cut cost without turning it off, lower `samplingPercentage` or remove evaluators. The results log group is retained when the stack is deleted, so delete it yourself once you no longer need the results.

## Dataset evaluations

Runs a JSON dataset of test conversations against a **deployed** AgentCore Runtime and scores the results with **AgentCore Evaluations**. This complements the online evaluation config in `packages/infra` (sampled live traffic): it scores a fixed set of cases on demand, for example before promoting a release.

### How it works

`run.py` wraps the AgentCore SDK's `OnDemandEvaluationDatasetRunner`:

1. **Invoke.** Each scenario gets one Runtime session. Its turns are sent in order to the Runtime's HTTPS endpoint with the eval user's bearer access token (the Runtime uses a CUSTOM_JWT authorizer, not SigV4).
2. **Wait.** The runner waits `--ingestion-delay` seconds (default 180) for CloudWatch to ingest the traces.
3. **Score.** Spans are collected from the Runtime log group (and `aws/spans`) and sent to the Evaluate API with the dataset's ground truth.

The runner's own session IDs don't satisfy the agent's principal-bound session check. `runtime_invoker.py` therefore derives the owner from the token, opens an owner-bound session per scenario, and relabels the collected spans (see its docstring).

`runner.py` adjusts the SDK runner in two places (see its docstring):
- ADOT's MCP client spans are left out of tool-level targets, because the Evaluate API rejects them.
- Trajectory evaluators are skipped for scenarios without `expected_trajectory`. Such a scenario, for example an off-topic request that should call no tools, simply has no trajectory line in the summary.

### Writing cases

Use the AgentCore [dataset schema](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/dataset-evaluations-schema.md); see `cases/example.json`. `cases/safety.json` holds the safety cases: a prompt injection asking for the system prompt, a request to cancel an order and one to pay (Aria has no tool for either), a request for other shoppers' personal data, a price-and-stock question the catalog can't answer, and the saved-items request, which must call `saved-items___get_saved_items`. Per scenario:

| Field | Used by |
| --- | --- |
| `turns[].input` | Sent as the user prompt, in order, within one session |
| `turns[].expected_response` | `Builtin.Correctness` |
| `assertions` | `Builtin.GoalSuccessRate` |
| `expected_trajectory` | `Builtin.Trajectory*Match`. Use the agent's tool names: local tools by name (`search_products`), Gateway tools as `<target>___<tool>` (`saved-items___get_saved_items`) |

Write assertions that hold for any catalog unless the stage uses the fixture catalog.

### Running

Create a dedicated eval user in the stage's Cognito pool, then sign in once to get an access token. `login.py` runs the web client's authorization code + PKCE flow on its registered `localhost:4000` callback, so stop the local web dev server first:

```bash
cd packages/agent
uv run python -m evals.login \
  --domain https://<prefix>.auth.<region>.amazoncognito.com \
  --client-id <AuthStack UserPoolClientId> --out ../../artifacts/eval-token

export ARIA_ACCESS_TOKEN="$(cat ../../artifacts/eval-token)"
uv run python -m evals.run evals/cases/example.json \
  --runtime-arn <AgentRuntime stack output RuntimeArn> --invoke
```

The token lasts one hour. The region and log group are derived from the Runtime ARN (`--log-group` overrides the log group).

The runner prints one line per scenario and evaluator and saves the raw results, including the judges' explanations and the Runtime session IDs, to `evals/results/` (gitignored). It exits non-zero if a scenario fails to run or an evaluator returns an error. `not scored` means missing coverage, not a pass. `ignored: ...` means the service didn't use some of the ground truth; check the dataset.

The default evaluators are the five online ones plus `Builtin.TrajectoryInOrderMatch` and `Builtin.Correctness`. Pass `--evaluator` (repeatable) to replace them, for example with the `catalogue_grounding` ID from the Evaluations stack's `CustomEvaluatorIds` output.

To gate a release on scores, pass `--min EVALUATOR=SCORE` (repeatable). The run then also exits non-zero when that evaluator's mean over every score in the run is below `SCORE`, or when it scored nothing; an evaluator the run doesn't use is refused before anything is invoked. For example:

```bash
uv run python -m evals.run evals/cases/safety.json --runtime-arn <RuntimeArn> --invoke \
  --min Builtin.GoalSuccessRate=0.8 --min Builtin.InstructionFollowing=0.8
```

### Before you run

- **Captured content.** The stage needs `operations.captureContent=true` and Transaction Search delivering to CloudWatch Logs (see [operations](operations.md)). Without captured conversation content, there's nothing to score.
- **Cost and side effects.** Every turn is a billed agent invocation. Every evaluator makes billed judge-model calls (tool-level evaluators run once per tool call). Turns are written to the eval user's Memory (and, with long-term memory on, distilled into preferences and facts), so use a dedicated eval user to keep test data away from real users and from later runs.
- **Credentials.** The AWS caller needs `logs:StartQuery` and `logs:GetQueryResults` on the log groups, plus AgentCore `Evaluate` and `GetEvaluator`. A failed CloudWatch query is logged as a warning and looks like "no spans", so check permissions first if every scenario comes back unscored.
- **Not in `pnpm check`.** These runs call live services. The unit tests in `tests/unit/test_evals.py` cover the runner offline.
